# 数据存储与数据库架构

## 目标与边界

本项目部署在 GitHub Pages，是静态站点，没有常驻后端进程、数据库服务或安全的服务端写入接口。因此不能把浏览器页面直接改成连接 PostgreSQL/MySQL，也不能把 SQLite 文件当作可并发访问的在线数据库。

采用分层存储：

| 数据域 | 权威来源 | 页面读取/本机存储 | 原则 |
| --- | --- | --- | --- |
| 股票基础资料、分组、交易计划 | `data/stocks.json` | 同源静态文件 | 人工维护、代码审查、版本控制 |
| 研报原始评分及来源 | `data/research-reports.json` | 同源静态文件 | 保留报告日期、来源、原始分及备选版本 |
| 基本面快照 | `data/fundamentals.json` | 同源静态文件 | 采集端更新；失败保留最后有效值 |
| 行情快照、K 线、指数历史 | `data/stock-quotes.json`、`data/stock-cache/`、`data/index-cache.json` | 同源静态文件 + 浏览器 IndexedDB | Actions 负责采集；页面只读；历史序列不可随意裁剪 |
| 机器评分、板块汇总 | 对应构建脚本生成 | 小型同源 JSON | 派生数据，可由原始数据重建，不作为第二份人工事实 |
| 浏览器行情缓存 | 同源静态文件为源 | IndexedDB；localStorage 兼容回退 | 缓存可丢弃、可重建，不作为行情权威数据 |
| 用户个人参数 | 用户当前设备 | 现有 localStorage | 不上传公开仓库，不与共享股票数据混存 |

## 为什么不把所有 JSON 换成服务端 SQL

1. GitHub Pages 只能托管静态资源，不能执行 SQL 查询或安全保存写入凭据。
2. 把 SQLite 二进制数据库提交到 Git 仓库会造成二进制 diff、并发写入冲突和历史膨胀。
3. 浏览器若要直接读取 SQLite，需要额外 WASM/Worker 与加载成本；对当前股票池规模没有明确收益。
4. 页面仍需要静态快照才能快速首屏和支持 GitHub Pages 部署。

因此，当前最合适的是：**Actions 采集/校验 + 结构化源数据 + 构建静态读模型 + 浏览器 IndexedDB 缓存**。只有未来引入有鉴权的服务端 API、多人协同编辑、复杂查询或实时写入时，再评估托管 PostgreSQL/SQLite 服务。

## IndexedDB 约定

- 数据库：`stock-helper-static-cache`；对象仓库：`snapshots`。
- Key 使用同源静态资源相对路径，避免不同页面重复缓存同一份文件。
- IndexedDB 是可重建缓存，不得覆盖或取代仓库中的权威数据。
- IndexedDB 不可用、打开失败、事务失败时回退 localStorage；localStorage 容量不足时允许放弃缓存，但不得影响网络读取。
- 后台刷新失败时保留最后一次成功缓存。
- 数据库连接在页面生命周期内复用；收到 `versionchange` 时关闭连接并允许后续重新打开。
- 后续如变更对象仓库结构，必须提升数据库版本并提供升级迁移；不得在不迁移的情况下更名或删除现有 store。

## 数据质量与迁移要求

- 所有采集数据必须保留来源、市场日期/报告期、更新时间和状态；缺失值保持 null，不用 0 或模拟值填充。
- 行情快照与历史 K 线应区分交易日期、采集时间和复权口径。
- 派生评分必须可重建，并保留评分规则版本；修改评分逻辑必须同步更新测试和说明。
- 迁移先增加新读路径并验证，再切换调用方；保留旧数据回滚窗口，禁止一次性删除仍被页面或回测引用的数据。
- 自动化写入必须串行化或具备冲突重试；同一文件不得并发覆盖。
- 任何数据库整理都不得改变鳄鱼纪律、交易信号、研报原始分和机器评分口径。

## 本轮已实施

- IndexedDB 连接从“每次读写重新 open/close”调整为页面级复用。
- 增加连接被版本升级要求关闭后的失效处理；数据库打开失败仍走既有 localStorage 回退。
- 增加连接复用测试，后续由独立 CI 工作流运行全部 Node 测试。
