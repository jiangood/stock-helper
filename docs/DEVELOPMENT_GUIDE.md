# 开发与维护指南

本文面向维护者及协作 AI，记录本仓库的实际开发方式、验证流程和高风险边界。若本文与代码、工作流不一致，以当前主分支代码和 GitHub Actions 实际配置为准，并在修改时同步更新本文。

## 1. 项目形态与关键约束

- 项目是部署在 GitHub Pages 的静态网站，没有常驻后端服务、服务端 SQL 数据库或安全写入 API。
- 页面从同源静态 JSON 读取数据；行情与基本面由 GitHub Actions 采集、校验和发布。
- 浏览器不得缓存行情、K 线、详情、评分、基本面等业务数据：不使用 IndexedDB、Cache API、WebSQL、localStorage 或内存 Map 保存响应；业务请求使用 `cache: 'no-store'`。
- localStorage 仅允许保存明确的用户偏好或本机输入设置。不要把用户设置误删，也不要把业务数据改回浏览器缓存。
- 数据缺失应明确表达为 null、缺记录或不可用状态，不得用 0、模拟行情或推测值填补。
- 派生读模型可重建，但不可将其误认为权威数据源；删除或迁移前必须检查所有页面、脚本、Actions 和测试的引用。

详细数据边界见 [数据库架构](DATABASE_ARCHITECTURE.md)。

## 3. 本地预览与验证

### 本地预览

仓库 README 当前提供的静态页面预览方式：

```bash
python -m http.server 8089
```

然后打开 `http://localhost:8089/`。

### 自动化测试

仓库不再保留统一的测试工作流，完整测试套件只在本地执行（参考环境：Node.js 22、Python 3.11）。CI 中仅个别工作流运行与其相关的单个测试文件（`asset-fingerprints.yml`、`stock-snapshot.yml`）。本地按以下顺序执行：

```bash
# 构建页面派生读模型
node scripts/build_sector_monthly.js
node scripts/build_product_comparison.js
node scripts/build_research_scores.js
node scripts/build_stock_detail_cache.js

# 检查缓存构建脚本语法并构建缓存清单
node --check scripts/build_cache_manifest.js
node scripts/build_cache_manifest.js

# 运行全部 JavaScript 测试
node --test tests/*.test.js

# 运行 Python 测试
python -m unittest discover -s tests -p 'test_*.py'

# 校验股票与缓存数据
node scripts/validate_stock_data.js
```

说明：
- 构建脚本可能更新 `data/` 下的派生文件。执行前后检查 `git status` 和 diff，不要把无关生成数据混入功能提交。
- Python 测试如提示缺少依赖，先查看对应 workflow 或脚本的安装步骤，不要擅自跳过测试并报告全部通过。
- GitHub Actions 是最终 CI 结果依据；本地未运行、未完成或失败的测试必须如实说明。

## 4. GitHub Actions 与数据发布

主要工作流（以当前 `.github/workflows/` 为准）：

触发约定：除 `asset-fingerprints.yml` 外，其余工作流只在定时任务或手动 `workflow_dispatch` 时运行；提交代码不会顺带抓取或发布数据，避免在非交易时段或盘中生成快照。需要立即刷新数据时手动触发对应工作流。

- `stock-snapshot.yml`：采集股票行情与 K 线，并在提交前运行 `tests/monthly-kline.test.js`。
- `fundamentals.yml`：刷新基本面快照。
- `build-static-cache.yml`：在上游采集工作流成功后（`workflow_run`）或手动触发时，统一重建详情缓存、评分、板块月线、商品及关联股票月线对比、manifest 和健康快照，并校验后发布。
- `business-data.yml`：更新商品数据，并重建商品及关联股票月线比较。
- `asset-fingerprints.yml`：页面或公共 CSS/JS 变化后，运行 `scripts/update_asset_fingerprints.js`，为 HTML 中实际引用的本地 CSS/JS 计算 SHA-256 前 12 位并更新 `?v=`；第三方 CDN、内联代码和业务 JSON 不参与。只有 HTML 指纹有变化时才提交到 master；工作流使用 `GITHUB_TOKEN` 提交，避免由自动提交递归触发工作流。

重要原则：
1. 采集失败或校验失败时保留最后一份有效数据，不发布不合格数据。
- 个股原生前复权月 K 缺失时，可用足量前复权日 K 按自然月聚合 OHLCV 作为兜底；聚合结果标记来源，不混用未复权日线，也不以插值补价格。
2. 数据没有实质变化时避免制造无意义提交。
3. 静态缓存发布工作流会从最新 master 重建，并在并发变化时重试；不要随意破坏其并发保护逻辑。
4. Actions 定时任务不是实时行情。页面应显示数据日期、来源和状态，不得将延迟快照描述为实时数据。
5. 检查工作流时区、触发条件、权限、并发组和失败日志；不要只看 workflow 名称判断其行为。

## 5. 标准代码修改流程

每次功能开发、Bug 修复、重构或页面优化：

1. 读取最新 master 的 README、相关 docs、目标文件、调用方、测试及工作流。
2. 检查当前 master 提交和目标文件版本，确认没有覆盖并发变更。
3. 默认直接在仓库主分支（当前为 `master`）修改；不创建功能分支，不创建 PR。
4. 按最小范围修改，复用已有模块、数据结构和样式约定；写入前重新确认目标文件 SHA，避免覆盖并发提交。
5. 检查引用、空值、异常处理、异步 Promise、DOM 节点、事件绑定、移动端布局和缓存版本。
6. 为关键逻辑增加或更新测试；运行与修改范围相关的测试，并尽可能运行完整 CI。
7. 检查 diff，确认没有意外改动数据文件、评分口径、交易规则或生成缓存。
8. 直接提交到主分支；如果主分支保护或权限阻止提交，不得绕过安全规则，应说明原因并继续完成可安全执行的工作。
9. 提交后核对主分支最新提交、修改文件和对应 Actions。工作流仍在运行时应标记为进行中，不能提前报告成功。

## 6. AI 协作与工具使用规则

本项目允许通过已连接的 GitHub 工具维护仓库。协作 AI 必须：

- 收到“执行”“开始”“按推荐来”“继续”等明确推进指令时，结合上下文直接开展工作，不重复询问已经明确的信息。
- 先检查当前会话可用的 GitHub 工具及授权，再决定可执行范围。不得因为不能访问用户本地电脑，就推断不能读写 GitHub 仓库。
- 优先使用 GitHub 工具读取文件、列出目录、更新文件、直接提交主分支和检查 Actions。
- 不要只输出代码片段或教程来替代用户要求的仓库修改。
- 工具调用失败后，记录具体失败环节，检查参数、分支、文件 SHA、权限和替代工具；能继续的步骤继续完成。
- 不得声称已修改、提交、创建 PR、合并或测试通过，除非有对应工具结果或 CI 记录证明。
- 明确区分“尚未尝试”“尝试失败”“部分完成”“已完成”。
- 如果工具能力确实不足，说明具体缺少的能力或授权、已尝试的替代路径，以及需要用户做的唯一必要动作。

## 7. 高风险修改检查表

以下变更必须格外谨慎，并检查所有共享调用方：

- 鳄鱼纪律与个股详情中的辅助判断规则。
- 研报原始评分、机器评分权重、阈值、数据日期及评分版本。
- 股票主数据、基本面字段、行情与 K 线复权口径。
- Actions 的数据发布、并发控制、失败保留和权限配置。
- 前端数据读取方式、浏览器缓存策略及静态缓存 manifest。

不得为追求页面简洁而隐藏重大风险或删除无法自动计算的纪律项。无法自动判断的项目应明确显示“无法计算”及原因，不得伪造通过。

## 8. 完成汇报格式

每次代码任务完成后简洁汇报：

1. 实际修改内容及涉及文件。
2. 工作分支和 PR 链接。
3. 是否合并 master，以及合并提交。
4. 测试命令和真实结果。

**最终原则：以可验证的实际交付为目标。先检查工具，再执行；遇到障碍先排查和寻找安全替代路径；不把工具限制泛化为无法完成，也不把未执行的操作说成已经完成。**

## 9. 生意社商品图表取数规范（顺酐方式）

本节是生意社商品历史价格采集的统一规范。新增或补齐生意社商品序列时，**以生意社原始价格走势图为唯一依据**，按顺酐的图表 OCR 方法取数。不能因为某商品有基准价文章、企业报价、年度统计或 Rawmex 表格，就把这些数据当作图表历史接入。

### 9.1 唯一认可的图表请求方式

优先使用顺酐已验证的通用图表接口：

```text
https://www.100ppi.com/graph/report.php?btime=YYYY-M-1&etime=YYYY-M-2&f=xht_agent_price&ppid=<商品图表PPID>
```

参数含义：

- `btime`：图表开始日期，按月取该月 1 日。
- `etime`：图表结束日期，按月取该月 2 日。
- `f=xht_agent_price`：顺酐方式使用的图表类型参数。
- `ppid`：该商品在此图表接口中的真实图表 ID。必须从生意社实际页面/图表请求中确认，不能猜测，也不能把商品目录 ID、文章 ID、另一种图表 URL 中的 `id` 或路径编号直接当作 `ppid`。

已知可复用的验证样例：

- 顺酐：`ppid=660`。示例：`https://www.100ppi.com/graph/report.php?btime=2020-4-1&etime=2020-4-2&f=xht_agent_price&ppid=660`。
- 粘胶短纤：`ppid=1017`。示例：`https://www.100ppi.com/graph/report.php?btime=2025-10-28&etime=2026-10-28&f=xht_agent_price&ppid=1017`。仍需按月请求并完成跨年份月初取点验证，才可正式接入。

### 9.2 新商品接入前必须完成的验证

1. 从生意社商品页面的真实图表请求中确认 `ppid`，记录商品名称、规格、价格类型、地区/工艺（如有）和单位。
2. 使用上述 `report.php` 模板分别请求至少三个不同年份的区间；至少包含较早历史年份和近期年份。
3. 每次都检查 HTTP 状态、响应内容确为有效 PNG、图表确实有价格曲线。HTTP 200 或返回一张图片本身不代表有数据；“无数据”图、空白图、错误页均判定失败。
4. 交叉检查图表标题、商品规格、单位及价格口径，防止把不同等级、工艺、地区或报价类型混成一条序列。
5. 只有跨年份请求均能得到可识别的价格曲线，且 OCR 质量检查通过，才允许接入自动采集。仅找到网页、文章、基准价或其他图表接口不算通过。

### 9.3 月初价格 OCR 规则

- 每个月请求该月 1 日至 2 日的图表，取价格曲线最左侧有效点，作为该月月初观测；不是月平均价，也不是月末价。
- OCR 识别纵轴价格刻度，以刻度像素位置与价格值做线性拟合，再定位图表最左侧蓝色价格线像素并换算价格。
- 沿用 `scripts/test_sunsirs_month_start_ocr.py` 的质量门槛：至少识别 4 个纵轴刻度，拟合 RMSE 不超过 8，左侧蓝线像素数量达到最低要求；同时检查图片尺寸、价格有效性和曲线是否存在。
- 采集记录必须标注来源图表 URL、观测日期、单位、OCR 方法、估算状态及质量信息。数值属于**图像估算值**，不是生意社原始报价，不能伪装成精确原始数据。
- 图表没有价格线、明确无数据、图片损坏、刻度不足、拟合误差超限或价格无效时，记录为缺失/null 或保留失败状态；不得插值、外推、用文章报价补齐或改用相近商品代替。
- 不同商品必须单独确认 `ppid`、规格和 OCR 图表坐标/颜色是否一致。不得假设顺酐的固定坐标、蓝色阈值和刻度范围对所有图表都适用；如图表布局不同，先独立校准并增加样本测试。

### 9.4 来源边界与期货例外

- 生意社商品历史价格统一按上述走势图方式取数。基准价文章、参考价快讯、企业报价、年度统计、Rawmex 表格等均不能替代走势图。
- 若找不到 `report.php` 对应的有效图表，或历史区间无法取图/无法可靠识别，**放弃该商品的生意社图表采集**，保持数据缺失，不继续寻找其他报价口径补位。
- 已有稳定、标准化期货行情接口的品种继续使用对应期货数据源，不纳入生意社图表补数范围。
- 不要因本规范而自动删除或覆盖现有历史数据。发现旧序列来自基准价/企业报价而非图表 OCR 时，应先标记来源不符合新规范，再单独评估迁移；不得把旧来源改标成图表估算。
